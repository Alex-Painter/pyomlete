# Omlete design

How the app is shaped and why. The principle behind every choice here is in [PRINCIPLES.md](PRINCIPLES.md): **eat better and reduce cognitive load**. For where things live in the code, see [AGENTS.md](../AGENTS.md).

This describes the October 2026 redesign as built. It is deliberately short; screenshots go stale, so check the app itself (or the `verify-omlete` feature map in `.claude/skills/verify-omlete/features/`) for what a screen looks like today.

## Context

The redesign started from a UX audit of the desktop and mobile apps in October 2026. Alex's priorities, in order:

1. **Making shopping lists is the top pain**, especially adding, removing and editing items. It has to take one gesture each.
2. **Discovery should be proactive and taste-based.** The app suggests recipes and lists from what you like, rather than waiting to be searched. Web search comes later, so the UI is built around suggestion cards any agent can fill.
3. **Mobile first, and carry over to iOS.** Prefer patterns with native iOS equivalents so a future native app is a port, not a rethink.

## Decisions

Each of these was settled in discussion; the reason is what to weigh before changing it.

| Decision | Why |
|---|---|
| Four separate modes: Explore, Plan, Shop, Cook | They used to blend into one list page, so no task had a screen built for it. |
| Plan stays its own mode, separate from Explore | Building the list is the top priority and deserves its own focused screen rather than sharing one with browsing. |
| Modes are entry points, not stages; the UI never changes because a step finished | People forget to tick things and shops have no signal. Cook can't wait on a "complete" list, and nothing should move or disappear on its own. |
| Shop works offline | Many shops have no reception, so a list must open and accept changes with no network. |
| Undo instead of confirm dialogs | Fewer decisions and taps; a mistake is one tap to reverse. |
| In Plan a tap on a list row opens the edit sheet and only the circle checks it off, Got it rows included; in Shop a tap anywhere on the row checks it. Web and iOS | Alex's rule: in Plan you are building the list, so a tap edits. Checking off is what you do in the shop, so only Shop checks on a tap. |
| The suggest-meals sheet moved off the list page into Discover | Suggestions on the list page got in the way of building the list. |
| Lists live on Home, with Plan a week above the fold | Lists are opened most and Plan a week is the most common action, so a separate Lists tab would add a hop. |
| Home leads with meals to cook from the current list | Opening the app to cook shouldn't mean opening the list first. |
| Chef's picks sit below Lists on Home | Suggestions shouldn't push the most common action out of reach. |
| Chef is the name of the suggestions agent | One named character for "the app suggests things" across Home, Discover and future features. |
| Clear is separate from "Not for me" | Clearing the feed is tidying, not a verdict on the food; mixing them would skew Chef's taste profile. |
| Detected timers in Cook | Alex liked them in the audit: times in the method become one-tap timers. |
| On iOS a cook is saved on the phone, recipe included: the step, servings, timers and an unsent rating survive closing Cook or the app being killed | A phone propped by the hob gets locked, switched away from and loses signal. The web keeps this in the page, so closing it loses a running timer. |
| On iOS, reopening Cook resumes within 8 hours and otherwise starts from the overview; a finished cook always starts over | Coming back mid-meal should find your place, and cooking the same recipe next week should not start on step 6. |
| iOS timers ring in the app with a sound and a haptic, with no notifications yet | A notification needs a permission prompt, which is a product decision of its own. A timer that ends while the app is in the background rings once when you come back. |
| On iOS a rating shows at once and is sent when it can be; one the server refuses is dropped without a message | There should never be an error to dismiss with a pan in the other hand. |
| Closing Cook returns to where it was opened: Home, the list or the recipe | Cook covers the screen it was opened from, so leaving it is not a navigation. On the web each step replaces the history entry rather than adding one, so the browser's back button leaves Cook too. |
| Back buttons go to the screen you came from, not a fixed parent | A recipe opened from a list should go back to the list, not the library. On the web `BackLink` steps back in the tab's history and uses its fixed destination only when the page was opened directly. Leaving Shop is a back too, so Back on the list after shopping doesn't reopen Shop. |
| On iOS each of the four tabs keeps its own stack, and Plan hides the tab bar | Switching tabs should not lose your place. Start shopping owns the bottom of Plan, and the tab bar would sit on top of it. The web shows both because its tab bar is not floating. |
| On iOS, finding ideas, saving a card and adding a recipe carry on when you leave the screen | Each waits on a model for up to a few minutes and has already cost money by the time you switch tabs. The app owns the work, not the screen. Finding ideas is one request, allowed 180 seconds where other requests get 20. |
| On iOS a Discover card that is saving cannot be dismissed or cleared | The server marks the card saved when the recipe is ready, which would bring a dismissed card back. The web allows the tap and has that bug. |
| On iOS a card whose save could not be sent reads "Couldn't save this one" with Try again | The web puts the card back as if nothing was tapped, which reads as the tap being ignored. |
| On iOS, Add to list that fails says so in the banner, and so does a card sent to a list whose recipe could not be made | The web ends the spinner and shows nothing. A failed card also drops out of Chef's picks on Home, as on the web, so there the banner is the only thing that can say the meal is not coming. |
| On iOS, news nobody tapped for (a save that failed in the background) waits while a banner with Undo is up | Replacing that banner would commit the change and take the Undo away at a moment the user did not choose. |
| On iOS, tapping a meal back on in Plan's library while its removal can still be undone is that Undo, and so is planning it on an evening, which also clears the evenings it was taken off, as on the web | The server still has the meal then, so asking it to add would answer "already there" and the removal would go through anyway. It also still has the meal on its old evenings, and planning it says where it goes now. |
| On iOS, Plan's library with no recipes offers Add a recipe and Browse Discover, and each switches tab, leaving Plan open under its own tab | The web links to both pages. On iOS both are tabs and Plan hides the tab bar, so without the buttons an empty library is a dead end. |
| On iOS, a list's changes reach the server in the order they were made: one made while an Undo banner holds an earlier one waits for the banner to settle, up to five seconds, even a check in Shop | The server has to apply them in order, as on the web. A removal it applied after a later change could undo that change there, such as an item edited after its meal was taken off, whose amount the removal would then work out again. |
| Adding a recipe on iOS is a job the server owns under a key the phone mints. The tap writes the key to the phone before anything is sent, the start names it (`PUT /api/recipe-jobs/{key}/link`, `/describe` or `/photos`), and the app asks how it went by the same key. Coming back to the app, a relaunch or the network returning picks the job up again: ask for it, and send the start again if the server has never heard of it | Making a recipe was one request of a minute or more, and iOS drops it when you switch apps while the server carries on and saves the recipe. The app could not tie the result back to Add, and a retry of a description or photos paid for a second model call and made a duplicate. An id the server minted did not close that: a start whose answer was lost left the phone with nothing to find the job by. With the key made first there is no such moment, and a start sent twice is one job, because the key is the document's `_id` and Mongo refuses the second. The web still waits on the one request, which a browser tab keeps open. |
| On iOS only a clear answer ends a recipe job: the server saying how it ended, refusing to start it, or the first start never leaving the phone. A start or a look that is not answered, a server fault and an answer the app cannot read are all tried again, less and less often, and after two the screen says which it is: waiting for a connection, or Omlete is having trouble | Once the phone has sent a job it cannot know whether the server has it, so an error would invite a second tap and a duplicate. A fault says nothing about the job, and a newer server may answer in words an older app does not know. |
| On iOS a recipe job is over eight minutes after the tap, whatever the server says or does not say. Add ends as a failure that says Omlete did not answer in time and to check your recipes, with what was typed still in the field. The start is only sent for the first two minutes | Without an end of its own the phone kept Add locked for as long as the server stayed silent, across relaunches. The server calls a job lost after six minutes, so a start sent within two cannot still be running at eight. The recipe may have been saved by a server that could not say so, which is why the message points at the library and the library is refreshed. |
| On iOS a tap on Add with no network, or no server at that address, says it could not reach Omlete at once and keeps what was typed | Those failures happen before a request can leave the phone, so no job can exist and there is nothing to wait for. This holds only for a job's first send: once a start has been answered, gone unanswered, or been replaced while still out, a later send that cannot leave is waited on like any other. A timeout or a dropped connection is different: the start may have arrived, so the job is kept and asked after. |
| Photos for a recipe job are not kept on the phone. If the app is killed before the upload arrived, the next launch says the photos did not reach Omlete and to choose them again | Six photos are too large for the app's settings store, and a job whose upload did arrive is followed as usual. A text job is sent again from the text saved with its key. |
| A recipe job whose recipe has been deleted by the time the phone reads it ends on an empty Add form with no message | Nothing failed, and there is no recipe to show. The library is refreshed. |
| A recipe job is stopped after five minutes, and one still working a minute after that is answered as failed when it is read. A server that is shutting down stops its own jobs and writes them as failed before it exits | The server runs a job in a task that lives in its memory. A deploy ends that task, and without the shutdown step Add would work on for six minutes; with it the phone hears on its next look. The read-time rule is the backstop for a server that is killed outright, and there is no sweep at startup because two instances overlap during a deploy and one would fail the other's jobs. Five minutes is longer than any honest job (the slowest is a page fetch and three model calls) and bounds what a job can spend. It does not promise that a job answered as failed saved nothing: a stop that lands while the recipe is being written can leave the recipe behind, and so can a job on a server that could not write how it ended. |
| At most four recipe jobs work at once on each server instance, counted from that instance's own running tasks; a photo must be a JPEG, PNG, GIF or WebP; a photos job takes up to six photos of up to 5 MB each, and a job's record is deleted after a day. One more start is answered 429, which the app shows as Omlete being busy | A start returns at once and the work is a model call somebody pays for, so nothing else limits how many run. One household makes one recipe at a time, the iOS picker takes six photos and re-encodes each no longer than 2000 px, 5 MB is the most the model takes for one image, and the phone has stopped asking about a job long before a day is up. |
| A Discover card's save is held to the recipe jobs' bounds: stopped after five minutes, and a card still saving a minute after that is answered as failed wherever it is read, can be saved again, which starts the work afresh, and can be cleared or dismissed. A card left saving by a server from before this rule has no start time and counts as lost. A server that is shutting down stops its own saves and writes them as failed | The save runs in a task in the server's memory, like a recipe job, and every deploy lost it and left the card saving for ever: the web said Saving and polled without end, and nothing could retry or clear the card. The reasons for each bound, and for deciding when read with no sweep at startup, are the recipe jobs' in the row above. It is the same failed state a card already had, so no client changed to show it. A save is not a recipe job: it has no key and no cap. |
| One run owns a card's save. Starting a save and writing how it ended are each one conditional update on the card's status and the start time of its save, so of two saves sent in the same instant one starts, and a run that finds the card saved again, cleared or dismissed writes nothing | Web and phone can both show Try again for the same card, and each tap started a task and paid for a model call. The end was a write of the whole card from a copy held for minutes, which put back a card cleared or dismissed meanwhile and overwrote a newer save. The start time names the run, so no extra field was needed. Clear decides a lost save by the same rule a read does: it reads the cards still saving and takes those the rule calls lost. |
| A save that puts its meal on a list adds it first and then writes the card once, as saved, or as failed with "The recipe was made, but it could not be added to your list. Try again." The card keeps its recipe, and saving a card whose recipe exists uses that recipe without asking a model | The card used to say saved before the meal was on the list. A phone fetches the list when it reads saved, so it fetched too early and never again, and a list that then failed turned a saved card failed after clients had acted on it. Keeping the recipe is what makes Try again finish the job and not make a second copy. The add and the write must fit the minute between the five-minute limit and the six-minute bound: ten seconds for the list and three tries at the write, 36 seconds at worst. A card with no recipe recorded can still be made twice: one saved from a title whose save was stopped, or could not be written, after the recipe was. |
| A timeout raised inside the making (a page or a model that did not answer) is that making's failure with its own words. Only the five-minute limit running out reads "The save was interrupted" | Both arrive as the same error, and a page that timed out was being logged as a save that ran past its limit. Recipe jobs tell them apart the same way. |
| On iOS a card is given up on eight minutes after the phone first saw it saving, each card on its own clock, and only by a feed that arrived after that and still says saving. A card given up on that the server later finishes is taken as a save that landed. When the server cannot be reached, polling rests after three failed fetches past the eight minutes, with the card left saving and nothing said, until the feed is next loaded. A clock put back fails no card: its eight minutes start again from the earlier reading | The server answers a lost save as failed after six minutes, so this only ends a save for a server that never says, and keeps the poll from running for ever. Eight is the bound a recipe job has on the phone. A fetch that fails has heard nothing: after the app was suspended for eight minutes the first poll to miss the server used to fail the card and say the meal was not on the list, when the server had most likely finished. The count used to be one for the whole feed, which failed a card saved late within seconds. |
| On iOS a feed asked for before a save was answered does not decide that card: the card stays saving, with the list it was sent to, until a feed asked for after the answer arrives | The older feed shows the card as it was. Taking it at its word dropped the list, so the list was never refreshed when the meal landed, and on a Try again it said the meal was not on the list. |
| On iOS, Try again on a card that was sent to a list sends it to that list again | The card failed on its way to a list, and a Try again that only saved it left the meal off the list with nothing to say so. The phone remembers the list only while it runs: after a relaunch Try again saves the card and no more. |
| On iOS, Home's Clear tidies only the picks nobody has acted on, and Discover's Clear all takes everything but a card still saving | A saved or failed card is never on Home, so clearing it from there would remove something the user did not see go. The web's Home Clear is the same. The phone's call says so (`only_new`), and the server then leaves a card that was saved or failed somewhere else after the phone last read the feed. The web sends no such field and clears every card it names, as before. |
| On iOS, Home with picks and no lists puts "No weeks planned yet" in the Lists section instead of over the whole screen | The full-screen message would cover the picks, and the picks alone would hide the invitation to start a list. With no picks it keeps the screen to itself, as before. |
| On iOS, Chef's picks wait for the lists to load, a feed that never loaded shows nothing on Home, and a refresh that fails keeps the picks already there | Picks under a spinner or a failure message would read as the screen being ready. Nobody asked for the section, so its failure is Discover's to report, and ideas already on screen are no worse for a failed refresh. |
| On iOS, Home with no lists waits for the suggestions to answer before showing "No weeks planned yet" | Otherwise the full-screen message shows on every launch and then rearranges itself around the picks. |
| On iOS, Home asks for the suggestion feed once, and again only if that failed; Discover, every change Chef makes and the app coming to the front still fetch it | Home only shows the feed, and refetching on every return to the tab cost a request each time for nothing. A card changed on another device shows on Home after a pull to refresh or the next return to the app. |
| The iOS app leaves a card whose status it does not know out of the feed, and shows a card marked saved with no recipe as failed | It used to treat both as new, which made them Home picks with a Save button whose effect it could not know. A status added on the server later is therefore invisible to builds that predate it, so add one only with the app change that shows it. |
| On iOS a recipe is edited in a sheet and saved in one go, and the save needs signal: one that cannot be sent leaves the sheet up with everything typed and says it is not saved | A save replaces the recipe's whole ingredient list on the server, so a queued one sent later could overwrite a newer copy. Lists queue because each change is small and safe to replay. |
| On iOS an edit with changes cannot be swiped away, and Cancel discards it at once with Undo, which reopens the editor as it was | A swipe is the gesture made by accident while scrolling a long form, and "Discard changes?" is the confirm dialog the app does without. An edit with no changes swipes away as any sheet does. |
| On iOS a quantity that is not a number stops the save and marks the ingredient; an emptied quantity is saved as none | The web saves 0 for what it cannot read, and a 0 nobody typed would go on every shopping list the recipe is added to. |
| On iOS an emptied title keeps the title the recipe had | A recipe with no title is a blank tile in the library, and an error to dismiss costs more than keeping the old name. The web saves the empty title. |
| On iOS the steps of a recipe being edited are moved by dragging a handle | It is how a list is reordered on iOS. The web has an up and a down arrow on each step. |
| On iOS, Edit recipe starts only from a copy the server gave this launch; if there is none yet the tap asks the server first, and says so if it cannot be had (a recipe deleted on the server says so on its page), and a save takes the note, group and on-list flag from the recipe as it is at that moment | A save replaces the whole recipe, so an edit begun from an old copy on the phone, or sent with a flag that has since changed, would put old values back. |
| On iOS, a discarded edit is offered back only while its recipe page is open and nothing the editor edits (title, steps, each ingredient's name, quantity, unit and aisle) has changed since | The Undo reopens the editor on that page, and a draft made from an older recipe would save the older values. A rating or an On list toggle made meanwhile does not count, because a save takes those from the recipe as it is then. |
| On iOS, an ingredient added in the editor joins the group of the ingredient before it. The web adds it with no group | Groups are not editable, and a row with none shows on the recipe page alone under a heading of its own, after the last group. |
| On iOS the cog is at the top left of each tab's first screen and pushes Settings onto that tab's stack | Each screen's own actions keep the top right, and the cog is in one place on all four tabs. Every change in Settings saves as it is made, so a sheet's Done or Cancel would mean nothing. The web puts the cog on the right. |
| On iOS deleting an aisle applies at once with Undo, and the save waits for the banner | The web asks first, which is the confirm dialog the app does without. Waiting means an Undo sends nothing and a delete that cannot be saved has one outcome to report. Another aisle change made during the banner is sent with the aisle still in its place, so the delete never goes out early. |
| On iOS an aisle change made with no signal is kept on the phone and sent when the app next comes to the front, the network returns or the aisles are next loaded. The order sent replaces whatever the server holds by then. Only a save the server refuses goes back to the server's order, and the banner says so | A delete settled as the app left, or an order the app was killed before sending, was lost without a word, and lists already work with no signal. The cost is that an order sent late undoes what another device did to the aisles meanwhile: the last one sent wins. This reverses the earlier rule that an aisle change needed signal and was never written to the phone. |
| On iOS the aisles can be changed only once the server has answered for them this launch | A save replaces the whole order, so one made from an old copy on the phone would put old aisles back. Until then Settings shows the saved order greyed out with Try again. An order still owed from an earlier launch is shown and sent first. |
| On iOS an aisle order the server keeps failing to save (unreachable, timed out, a 5xx) stays owed and shown. It is tried once each time the app comes to the front, the network returns, the aisles are loaded or the order is changed, with no timer in between. The aisles still load meanwhile, so they can be changed, and a load does not replace the order that is owed | A save that kept failing used to stop every load behind it, which after a relaunch left Settings greyed out with an order the user could not even replace. The owed order is the user's last word, so the server's answer to a load waits behind it and shows only if the save is refused. No timer, because the times the app already retries at are the times a person is looking. |
| On iOS an owed aisle order is always sent, even when it is the order the server last answered with, and the phone then shows the order the save answers with | A save that timed out may have been stored anyway, then or later, so the last answer is not proof of what the server holds: putting the old order back on the phone and sending nothing left the server on the new one. The answer is the list as the server cleaned it, so an aisle it dropped as a repeat goes from the phone at once and not at the next load. |
| On iOS an aisle cannot be given a name another aisle has, whatever its case, by adding or by renaming. A name that is refused stays in its field with the reason. An emptied name is not refused: the field goes back to the old name with no message | Lists group by name, so two aisles with one name are one aisle that is listed twice. The web checks this when adding and not when renaming. Keeping the text means a slip is put right and not retyped. An emptied field has no slip to put right, and the old name is the only thing it can have meant. |
| The server stores a clean aisle list whatever it is sent: names trimmed, empty ones dropped, and a name that repeats an earlier one in any case (compared with `casefold()`, so Straße and STRASSE are one) dropped | The rules lived only in the iOS app, and the web's rename could store two aisles with one name. It cleans and does not refuse, because every client sends its whole list and none expects a 422. On the web, renaming an aisle to another's name now leaves one aisle where it left two. |
| On iOS a new item is not filed under an aisle that is no longer in the order | The server remembers each ingredient's aisle by name and would put milk back under an aisle that was renamed or deleted. The app keeps its own guess then. |
| Renaming or deleting an aisle moves no item, on iOS as on the web | The server keeps each item's aisle as text and does not rewrite it. Those items stay grouped under the old name, after every aisle still in the order, and the item's aisle picker still offers the old name, until they are moved. Settings says so under the list. Rewriting them belongs on the server, where every list and recipe can be reached. |
| On iOS an aisle is moved by dragging its handle | It is how a list is reordered on iOS. The web has a handle and an up and a down arrow on each aisle. |
| Settings behind a cog, Add as a plain tab | A profile icon promised more than it did, and a raised plus button looked out of place. |
| Plan is organised around the week. A week is a list with seven days, each of which can hold a meal | The shopping list stays built from the meals, so planning dinners and making the list are one job. A list with no week works as before. |
| Meals without a day stay on the list as any-day meals, and clearing a day keeps its meal on the list | Many people shop for five meals and decide on the night which one to cook. |
| The week starts on the usual shop day, Saturday unless changed in Settings | The plan runs from one shop to the next, not from Monday to Sunday. |
| Each meal on a list has a Cooked tick (`cooked` on the list, `PUT /api/lists/{id}/recipes/{recipe_id}/cooked`). It is set on the day card, a meal's action sheet, a plain list's meal card, or by Finish in Cook opened from that list, which shows the tick to take it back. Home's Cook from your list and the meal chips mark cooked meals in place | Seeing at a glance what's left to cook this week is less to remember. A cooked meal never moves, hides or changes the layout, because nothing should change on its own when a step finishes. Finishing in Cook is the moment you know it was cooked, so it is ticked for you rather than asking. Removing a meal forgets the tick, and a duplicated list starts with nothing cooked |
| The calendar and suggestions only ever suggest a day's status. They never hide or move a meal | Nothing moves on its own. A meal stays where the person put it until they move it. |
| Plan a week plans this week, or next week on the day before the shop, and opens that week's list if it already exists | People plan the evening before they shop, and a second tap should never make a second copy of the same week. |
| On iOS the shop day is fetched with Home's lists and saved on the phone with them. Plan a week uses the saved one, so it opens an existing week with no signal; a phone that has never been told waits for a load before choosing a week, and is Saturday only if the server cannot say | The web waits for the setting before it chooses a week, so it never makes a week starting on the wrong day. A phone is often offline, and a button that waited for a fetch there would be dead. Only a phone that has never loaded the setting has nothing better than the default. |
| Plan shows the meal library inline, searchable and sorted by Not had lately, instead of the Add meals sheet | Scanning a modal list in no useful order was the slowest part of planning. Not had lately gives variety without remembering what you ate. Discover picks are no longer shown on Plan; they stay on Discover and Home. |
| On a phone, while you type in Chef's sheet it fills the space above the keyboard, whatever height it was at, and goes back on blur | Mobile Safari opens the keyboard without shrinking the layout viewport, so the sheet stayed on top of the tab bar with a blank band between it and the keyboard. Typing is when you want to see the conversation, and the tab bar is no use then. |
| Above Chef's message box a line shows what Chef is looking at: the recipe or list on screen by name (Recipe and List until the name loads), or else the page with a globe | Chef already reads the page it was asked from, so "this list" needs no name. Showing it makes that visible, so you know what "this" means before you send. |

## Home plus four modes

People use Omlete in four distinct ways, and the old app blended them into one list page. Each now has its own screen and layout:

| Mode | Screens | What it's for |
|---|---|---|
| **Explore** | `/discover`, `/recipes`, `/recipe/$id`, `/create` | Finding something to cook: Chef's suggestions, your library, adding a recipe from a link, description or photos |
| **Plan** | `/list/$id` | Building a shopping list: add meals, quick-add and paste items, edit and delete with Undo |
| **Shop** | `/shop/$id` | In the shop: fullscreen, large rows, works with no signal |
| **Cook** | `/cook/$id` | At the stove: one step at a time, scaled amounts, detected timers, a rating at the end |

**Home** (`/`) is where you land and the hub between them. It is a stack of sections, in order of how often they're used:

1. **Cook from your list**: meals on the current list, one tap into Cook.
2. **Lists**, with **Plan a week** beside the heading, the most common action, so it stays above the fold.
3. **Chef's picks**: Chef's newest suggestions, with See all going to Discover.

The phone tab bar on the web is Home, Discover, Chef, Recipes; the Chef tab opens Chef's sheet over the current screen, and Add a recipe is a link from Chef and from Recipes. Settings sits behind the cog in each page header.

## Modes are entry points, not stages

The UI never changes because another step finished. You can go from any mode to any other at any time, and finishing one never moves you into the next.

- **Nothing has to be checked off.** People forget to tick items, and shops often have no signal. Cook never depends on the list being done, and Shop has no "done" step.
- **Nothing is archived or hidden** because a list looks finished. Lists stay where they are until you delete them.
- **Shop works offline.** Every list change is written to the phone first (`client/src/lib/offline.ts`) and synced when the network allows. A list opened at home still opens in the shop, and the service worker (`client/public/sw.js`, production only) keeps the app shell loading.
- **Destructive actions are instant with Undo** rather than an "Are you sure?" dialog.

## Chef

Chef is the proactive suggestions agent. Its job is the "more variety" half of the principle: new ideas reach you without you going looking.

- **Cards, not recipes.** A suggestion is a title, a reason it suits you, and optionally a photo and source link (`SuggestionDocument`). Saving one turns it into a recipe in the background; from a link it's imported, otherwise Claude writes it.
- **Where cards come from.** Today, Refresh on Discover (`POST /api/suggestions/refresh`) asks Claude for ideas from your taste: ratings, "Not for me" dismissals, recent lists and Tune settings. Any agent can also post cards to `POST /api/suggestions/`.
- **Taste is learned, not configured.** Ratings after cooking and "Not for me" are the signals. **Clear** (`POST /api/suggestions/clear`) is different: it tidies the feed and teaches Chef nothing, so you can clear without worrying about skewing future picks.

## Planned (v2)
